# ZLS 命名导入跳转失效排查

## 背景

本项目把渲染层拆成了以模块为单位的编译单元：`_types`（后端中立的公共类型）、
`backend`（D3D11/Vulkan 两套实现，二选一）、宿主用的引擎模块。后端是按平台条件编译的——
Windows 上选 D3D11 或 Vulkan，非 Windows 只有 Vulkan。**没被选中的后端连模块都不会创建**，
这是刻意设计：依赖也按平台懒加载，不用的平台不该碰那些包。

排查问题时我在 **Linux** 上，用 **Zed + ZLS**。发现一个奇怪现象：两处写法完全相同的
`@import("render_types")`，一处在门面文件里能点击跳转，另一处在 D3D11 后端文件里点击没反应。
而 `zig build` 完全不报错——D3D11 文件在 Linux 上本来就是死代码。

这个现象的根子在 Zig 模块系统的机制本身，和具体项目无关，下面按原理讲。

## 原理

### 1. 命名导入是模块属性，不是文件属性

Zig 解决 `@import("xxx")` 有两条路径，语义完全不同：

- **相对路径**：`@import("../foo.zig")`。被引入的文件会**并入当前模块**，它自己再用的
  相对导入也在同一个模块语境下。
- **名字**：`@import("xxx")`。这里的 `xxx` 不是路径，是**在别处注册过的模块别名**。
  模块是谁建的？`build.zig`。创建模块时`imports` 列出"这个模块能看见哪些别的模块"。

关键推论：**一个 `@import("xxx")` 能否成立，只取决于写这行的文件所属的那个模块，
有没有把 `xxx` 挂进自己的 import 表**。同一个字符串，在 A 模块的文件里合法、
在 B 模块的文件里不存在，是常态。它不是"全项目全局可见"的东西。

于是文件属于哪个模块就成了问题。归属规则：从某个模块的 root 文件出发，沿**相对导入**
一路 reachable 的文件都属于那个模块。不在任何 root 的可达闭包里的文件，不属于任何模块，
对编译器来说是死代码，对 ZLS 来说更是"查无此人"。

### 2. 跨模块共享一个类型 = 两边都挂同一个模块

上面第 1 点直接推出一条工程规则：想让两个模块用上**同一个**类型定义（而不是各自拷贝
一份不兼容的类型），不能靠文件，得靠模块。做法是把那个类型文件单独建成模块，然后
**在每个需要它的模块的 imports 里都挂一份**。只要漏挂一边，那一边的名字就解析不了。

### 3. ZLS 是在"跑"你的构建，不是在"读"你的代码

ZLS 解析命名导入的方式：实际执行一遍 `build.zig`（构建描述本身是可执行代码），收集
本次配置**真正创建**了哪些模块、各自的 imports、各 artifact 的 root 文件，再据此判断
每个文件属于哪个模块、它能否看见某个别名。

这里有个容易忽略的间隙：`build.zig` 是程序，`if` 分支和 `zig` 编译器看到的分支并不必然一致。
编译器判断"某分支是否被编译"，依据的是运行时入口条件（目标平台、选项）；而 ZLS 拿到的
是"某个具体主机上跑出来的那次配置"。两者对**会被编译的代码**通常一致——没被选中的分支
确实不进编译，所以编译正确性不受影响；但"没进编译"同时意味着"不进模块图"，于是：

> **编译正确性 ≠ 编辑器信息。** 一份合法、可能将来会被编译的代码，只要它当前一次构建配置
> 里所属的模块没被创建，编辑器的解析就失联。ZLS 无法假装一个模块存在——那才是真的
> 误报诊断。

再叠加一层：多平台项目最终只有一个平台是你的开发主机。**ZLS 的能力上限就是那次主机
上的配置**，它天然看不到"另一半代码"的模块语境。这不是 bug，是按需编译的固有代价：
要让编辑器看见，就得让模块图包含它——即使它并不被编译。

## 项目里的印证

套到本项目：Linux 配置下 D3D11 后端模块**从未创建**，它的文件全都不在任一模块的可达
闭包里——跳转失效的是整个目录，不只一处。而门面文件经相对路径并入引擎模块，引擎的
imports 恒定包含公共类型模块，所以那边正常。Vulkan 侧的文件同理不受影响。

备选修法是把 D3D11 模块改成无条件创建（artifact 仍不引用它，不参与编译），让 Linux 的
模块图也" taxed "一份它的 imports。代价是并不需要的平台包会被拉取登记，与懒加载的精神
相悖，故保持现状，接受编辑器看不见那一只目录的命名导入。

## 小结

1. 命名导入按**文件所属模块**的 import 表解析；模块看 build.zig，不看目录结构。
2. 共享类型靠"独立类型模块 + 各使用方都挂同一份"，漏挂即断。
3. ZLS 的世界 = 主机上跑出的那一次 build.zig 的输出。平台条件创建的模块，其文件在
   其它平台上"存在于磁盘、缺席于模块图"：合法但编辑器失明。
4. 项目开箱即用的验证方式也随之分家：被条件排除的代码，诊断要靠交叉编译或目标机器，
   ZLS 帮不上忙。
