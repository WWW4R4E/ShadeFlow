# 资源导入（glTF / PNG）搭建计划

## 目标与范围

给引擎加资源导入，分三块推进：

1. **渲染层补能力**：纹理（`createTexture` + 采样）与 u32 索引 —— 这是其他一切的地基；
2. **`src/engine/asset/`**：纯 CPU 侧的解析器，输入文件字节，输出**后端中立的中间表示（IR）**，不碰任何 GPU 面；
3. **集成**：Engine 消费 IR，变成 RenderObject（顶点/索引缓冲 + 材质 + 纹理）。

范围裁剪（v1 明确不做，避免一开始摊子太大）：

| 做 | 不做（v2+） |
|---|---|
| glTF 2.0 核心子集：mesh / primitive / 节点 TRS / PBR metallic-roughness 材质 | 蒙皮、动画、多 UV、法线贴图、KHR 扩展 |
| `.gltf`（JSON + 外链 `.bin` / 图片文件） | GLB 容器（就是加个文件头分包，很薄，后补）、`data:` URI（base64，`std.base64` 现成） |
| PNG：8bit、非隔行、全部颜色类型 | 16bit、Adam7 隔行（碰到就报明确错误）、JPEG |
| 无 mipmap、无 sRGB 规范化（见"渲染侧决策"） | mipmap 生成、色彩管理 |

## 一、准备知识：这仨东西到底是什么

### 1.1 glTF = 一份 JSON + 几段二进制

glTF 2.0 的本质是「图形界的 obj+mtl 换代品」：场景结构、网格、材质全用 JSON 描述，
**实际数据（顶点坐标、索引）不在 JSON 里**，而在二进制 buffer 里。JSON 里只有
「去哪取、怎么解读」的元信息。四个核心概念，理解它们 = 理解 glTF：

```
JSON                                二进制
nodes ── 引用 ──> meshes ── 引用 ──> primitives ── 引用 ──> accessors ──> bufferViews ──> buffers
                                                    │
materials / textures ───────────────────────────────┘（position/normal/texcoord...）
```

- **buffer**：一段裸字节（`.bin` 文件）。没有任何语义，就是内存。
- **bufferView**：buffer 上的一条切片记录（offset + length + byteStride）。
  一个 buffer 上可以切出几十条 view，顶点、索引、材质参数混住在同一块内存。
- **accessor**：对 bufferView 的"读法"。声明组件类型（`componentsType`）、
  元素数量、以及**数据的实际含义**（POSITION 还是 NORMAL）。普通标量/向量情况下，
  POSITION/REQUIRED 的 accessor **必须**带 `min/max` —— 这个正好白送我们 AABB 拾取。
- **primitive**：一份可绘制单元 = 一组属性 accessor 引用 + 索引 accessor + 材质。
  **一个 mesh 可以有多个 primitive**（比如身子和枪套材质不同）——集成时一个
  primitive 对应我们的一个（Indexed）RenderObject，别按 mesh 算。

两个 API 细节，手上一定要 check：

- **`componentType`**：索引可能不止一种宽度！`5121`=u8、`5123`=u16、`5125`=u32。
  别假设 u16，要读字段（这也是我们为什么要先做 u32 索引迁移）。
- **`normalized`**：属性值可能是 u8/u16 且声明为 normalized（常见于旧模型的
  COLOR 属性）——读取时要在 float 归一化（u8: `x / 255.0`）。v1 可以先记录
  「遇到就报错」，但解析器结构要给它留位。

**坐标约定**：glTF 是 **Y 向上、右手系**。跟引擎现有的相机/世界系对不对得上，
要对着 `笔记/` 里的相机推导看一眼；对不上就在导入侧加一个固定变换（一次性
写死的 flip 矩阵），**别把翻转变换器散落在各处**。三角形绕序：glTF 规定从
正面看是逆时针（CCW）。如果导入的模型"里外翻转"，八成就是绕序/剔除不匹配，
先试着换 `RasterState.cull` 判断，别急着改顶点。

**材质**：PBR metallic-roughness 是 2.0 核心自带，字段就在材质里：
- `baseColorFactor: [r,g,b,a]`（可选）
- `baseColorTexture`（可选，经 `textures -> images -> bufferView/uri`）
- `metallicFactor` / `roughnessFactor`（可选，默认 1）
v1 的策略：没有纹理/材质时给默认值（白 1,1,1,1、metallic=1、roughness=1），
跟 glTF 规范默认语义对齐。

### 1.2 PNG = 一堆 chunk + zlib + unfilter

PNG 文件就是一个 **chunk 序列**（每 chunk：4 字节长度 + 4 字节类型 + 数据 + CRC）。
解码只需要仨：

| chunk | 内容 |
|---|---|
| `IHDR` | **必有且第一个**：宽、高、位深（8/16）、颜色类型、隔行方式 |
| `IDAT` | 像素**zlib 塑流**（可能有多个连续 IDAT，要拼接） |
| `IEND` | 结束标记（可选校验） |

颜色类型表（v1 全支持）：

| 类型 | 含义 | 解码后我们转成 |
|---|---|---|
| 0 | 灰度 | RGBA（r=g=b=灰度，a=255）→ `R8_UNORM` 也行，v1 统一 RGBA 简化 |
| 2 | RGB | RGBA（a=255） |
| 3 | 调色板 | RGBA（调色板在 `PLTE`，透明信息在 `tRNS`，都要读） |
| 4 | 灰度+α | RGBA |
| 6 | RGBA | 原样 |

**解码流水线**（这是 PNG 的灵魂，三步）：

1. 用 **zlib-inflate**（`std.compress.flate`，container 要指 `.zlib`，不是裸 deflate）；
2. 把解出来的原始流切成「每行 1 字节 filter 标记 + w*bpp 字节数据」；
3. **逐行 unfilter**：按上一行/左邻等解出真实像素。5 种滤波器，其中
   `Average`/`Paeth` 有点小公式，其余是加减 XOR。**这是 Rust/手写 many
   人栽的第一个跟头：忘了每个滤波器要有 padding 字节维度**，尤其是 bpp
   不是 3 的倍数时（比如调色板 bpp=1，一次比较要跨 1 字节）。

**这两个老大难**：16bit（每通道 2 字节大端）和 Adam7 隔行（把图拆成 7 个
子图分别扫）—— v1 直接报"PNG xxx 不支持，请转 8bit 非隔行"，比写一大堆
解析器中途出错好得多。

### 1.3 纹理上 GPU：数据怎么进纹理

不管哪个后端，把 CPU 像素变成可采样的纹理都是这条链：

```
CPU pixels ──(staging)──> GPU image ──(layout 转换)──> shader 可采样
```

- **D3D11**：最省事。`CreateTexture2D` 时直接传 `D3D11_SUBRESOURCE_DATA`
  初始数据，驱动顺便替你搬到显存。采样要 `SRV`（`CreateShaderResourceView`）
  + `PSSetShaderResources` 绑到着色器的 `t` 寄存器，配 `SamplerState`（`s`）。
- **Vulkan**：规矩多，枚举一遍照抄就行：
  1. `vkCreateImage`（`VK_IMAGE_USAGE_TRANSFER_DST | SAMPLED`），
     查 `vkGetPhysicalDeviceMemoryProperties` 分配一次 `DeviceMemory`；
  2. 建 **staging buffer**（`HOST_VISIBLE` 的 `USAGE_TRANSFER_SRC`），
     `vkMapMemory` 塞像素；
  3. 录一条命令缓冲：`cmdCopyBufferToImage`，前后用 image memory barrier
     转换 layout：`UNDEFINED → TRANSFER_DST_OPTIMAL → SHADER_READ_ONLY_OPTIMAL`；
  4. 建 `ImageView` + `Sampler`，`Descriptor.zig` 目前只挂常量缓冲，
     **要加 texture+sampler 绑定槽**。

着色器要补：HLSL 写 `Texture2D base_color : register(t0); SamplerState
base_color_sampler : register(s0);`，GLSL 对应 `layout(binding=...) uniform
sampler2D`。**注意 fxc/glslc 两边的 binding 对应关系要手工保持一致**（现状
shader 靠源码双维护，这会是新交叉点）。

## 二、渲染侧的两个前置决策

### 2.1 索引 u16 → u32（建议直接换代，不保留两种）

现状：`Geometry.indices: []u16`，vitex 数超过 65535 就废（glTF 模型随便超）。

- `Types.zig` 可以先不加 `IndexType` 枚举：**直接全改 u32**，签名
  `createIndexBuffer([]const u32)`，draw 也只收 u32。少一个分支，渲染层
  一次写干净。
- 后端实现：D3D11 是 `DXGI_FORMAT_R32_UINT`，Vulkan 是 `VK_INDEX_TYPE_UINT32`。
- `GeometryGenerators.zig` 的立方体/球索引数组跟着改类型（数量不多）。
- shader 里如果是 u32x4 打包索引也要扩.

### 2.2 纹理与描述符策略：v1 全局单纹理

`Descriptor.zig` 目前只有常量缓冲（环形缓冲 + dynamic offset）。给每个
对象独立描述符集分配会让 v1 复杂化；**v1 只做「一次绑一张」**：
- `Renderer.setTexture(tex)` 目前的大多数场景一次只采一张 baseColor 纹理，
  dump 的画面切换足以展示「材质多样」；
- 集成描述符布局加 `combined image sampler` 槽（或者分离 `SAMPLED_IMAGE`
  + `SAMPLER`，Vulkan 推荐分离，更灵活），D3D11 对应绑 SRV+Sampler；
- v2 上 atlas/bindless 的时候 layout 再重整。别为未来设计，先把链路跑通。

### 2.3 sRGB：先记下，不解决

着色器现在没有光照计算，纹理直接乘系数输出。理论上 baseColor 属于 sRGB
数据，光照前要转线性；但 v1 没有光照，转不转视觉上都算"看着还行"的做法。
**决策：v1 用 UNORM 格式直接透传**，等加光照时再统一升 sRGB 传输函数
（Vulkan 换 `SRGB` 格式、D3D11 换 `DXGI_FORMAT_R8G8B8A8_UNORM_SRGB`，
改动点就在格式枚举那里）。这里别边走边改，一次规划好格式枚举。

## 三、分阶段计划（顺序有依赖，别乱跳）

### 阶段 0 —— u32 索引迁移（半天）

改 `Types.zig`（如果有索引相关类型）→ 两个后端 `createIndexBuffer` /
`drawIndexed` → `GeometryGenerators` → `zig build run` 目视不变。这是
独立改动，**单独一个提交**，后面谁来都建立在它之上。

### 阶段 1 —— 渲染层 Texture 落地（2~3 天，跨两个后端）

1. `asset/Types.zig` 加一个 `TextureData { width, height, pixels: []u8 (rgba8) }`
   （先手工造）。其实这个也可以等 asset 阶段，先在后端里造个棋盘格也行。
2. 后端契约加方法（`backend/mod.zig` 的 `comptime` `required` 数组记得加，
   缺了编译期报错——这是现成机制）：
   ```zig
   createTexture(width: u32, height: u32, pixels: []const u8) !Texture
   loadTexture(tex: *const Texture, slot: u32) void
   ```
   （`loadTexture` 的接收方式按 D3D11/Vulkan 哪边更像自然来定，俩都能跑就好）
3. Vulkan 侧走 staging + barrier 三段式（参考上面 1.3 的清单），D3D11 侧
   `CreateTexture2D` 直接带初始数据 + `SRV`。
4. 着色器加采样，先用棋盘格纹理验证两个后端显示一致。
5. **在引擎根直接用硬编码棋盘格纹理把链路验通，asset 还没影子**——这步的
   价值是把 GPU 侧的全部不确定性消灭在解析器动手之前。

### 阶段 2 —— `asset/` 目录立骨架（半天）

```
src/engine/asset/
  Types.zig     # IR：SceneGraph / MeshIR / MaterialIR / TextureData
  Gltf.zig      # glTF 解析，v2 加 GLB/data URI
  Png.zig       # PNG 解码
```

- **`Types.zig` 只放纯定义**（结构体 + 解析函数签名），不 import 任何解析实现
  ——这是为了它可以被 `zig build test` 侧单独测，也可以被引擎/解析器双向用，
  不会循环。
- IR 设计要点（贴着"反解析方便"来，而不是贴"方便渲染"来）：
  ```zig
  pub const MeshData = struct {
      vertices: []Vertex,         // 引擎自己的交错顶点（复用 render 的 Vertex）
      indices: []u32,             // 已统一成 u32
      aabb: Aabb,                 // 直接吃 accessor 的 min/max
  };
  pub const MaterialData = struct {
      base_color_factor: [4]f32,  // 默认 {1,1,1,1}
      base_color_texture: ?TextureData = null,
      metallic_factor: f32 = 1.0,
      roughness_factor: f32 = 1.0,
  };
  ```
  Mesh 用**引擎 Vertex 结构**而不是 glTF 原始属性数组 —— 解析时就完成
  转换（交错化 + 延迟组合），消费侧拿到手就能 `createVertexBuffer`。
  转换发生在解析器里有个好处：内存顺序（解 contiguous 然后交错化）
  在一处做完，引擎不再二次处理。
- **所有指针/切片都标注 allocator 语义**：v1 建议全部走一个 `std.heap.ArenaAllocator`
  ——解析、缓冲分发、纹理都从同一个 arena 拿，加载完整个场景的销毁只
  需要 `arena.deinit()`，省得追踪十几种零散分配。

### 阶段 3 —— Png.zig（1~2 天，纯 CPU，非常好测）

按上面 1.2 清单从零写。**解码与" pixel 格式归一化"本就是纯函数，
单测就用真实文件做 fixture** —— 在 `assets/testimg/` 放几个色卡 PNG
（最好手工用 Python/ImageMagick 生成覆盖 5 种颜色类型 + 灰度 + 调色板 +
透明），断言像素值。解析入口签名建议：
```zig
pub fn decode(allocator: Allocator, bytes: []const u8) !TextureData
```
（收完整文件字节而不是文件路径，测试就不用碰磁盘。应用层 `Io.Dir.readFileAlloc`
 读进来才调它。）

### 阶段 4 —— Gltf.zig（2~3 天）

1. 用 `std.json` 的 static 解析（`parseFromSlice`，`.{ .ignore_unknown_fields = true }`
   处理它不认识的 extension —— glTF 生态 extension 多得很，.ignore 决不能省），
   schema 结构体手写，只收我们关心的字段。
2. **JSON 解析出来的是"引用+语义"，实际读数据靠 accessor 手工读**：写一个
   `readAccessorFloat(accessor, bufferView, buffer_data) []f32` 之类的
   泛型/闭包工具，内部处理 componentType / normalized / sparse(报错)。
3. 把 primitive 转成 `MeshData`：POSITION 拉点、NORMAL 拉法线（没有就兜
   `{0,1,0}`，纯光栅也无所谓）、TEXCOORD_0 拉 uv（v Take 的时候**要 1-v**
   —— glTF 的 v 朝下，纹理库多半朝上，这是最经典的"模型贴反了"来源，
   先记着这个方向上的怀疑）。
4. 索引 U8/U16/U32 全收，出 `[]u32`。
5. node 树遍历，拿 world TRS 拼成 Transform；**v1 不处理复杂场景**，只
   遍历到一个 mesh-node 就产出一组 `MeshData + MaterialData + Transform`。
6. **fixture 测试**：`assets/models/` 放 2~3 个*.gltf + .bin + 贴图进测试
   （[glTF-Sample-Models](https://github.com/KhronosGroup/glTF-Sample-Models)
   挑"最小体积，多 primitive + 索引"的，比如 Box/fence 材质变体），断言：
   accessor 数量对、顶点数一致、AABB 与 min/max 一致。

### 阶段 5 —— Engine 集成 + tests.zig 全接（1~2 天）

- `Engine` 加一个类似 `loadGltfScene(scene: asset_ir.GltfScene)`（或直接
  `loadGltfFile(path)`，Engine 内管读文件）：
  每个 `MeshData -> createVertexBuffer/createIndexBuffer`，每个primitive
  一个 Indexed RenderObject，材质 baseColor 纹理 `createTexture`，
  Transform 进 render_object。`local_aabb` 填 accessor 的 min/max， Picker
  就已经覆盖 glTF 模型（这步是白捡的）。
- **别忘了**：`src/tests.zig` 新测试文件要显式加一行（AGENTS.md 有警告，
  否则静默不跑）；`render/Types.zig` 的测试如果新加也得单独 target。
- 到这一步用 `zig build run` 载入一个真实 glTF 目视确认，Y-up、绕序、
  纹理问题都在这步暴露。

### 阶段 6 —— Windows ABI 桥接（可选，放最后）

WinUI 侧目前用不上纹理（C# 还没翻译输入之外的接口）；如果之后要给 WinUI
暴露 `ShadeFlow_LoadGltf`，**记得同步 `ShadeFlowNative.cs` 的 DllImport**
（AGENTS.md 有要求，一处对不齐就是 `DllImport` 找不到符号）。建议这段
单独提交，因为没法在 Linux 上验证，`zig build dll` 只能在 Windows 侧跑。

## 四、踩坑清单（按提交顺序集中列一次）

**Zig / 工程侧**
- `zig build` 时**同一个文件不能同时是两个模块的根**（阶段 1 给
  `Types.zig` 做成独立模块后，相对 import 它就报错）——这是这次 import
  整理刚踩过的，照拓眉易犯。
- 新文件测试要在 `src/tests.zig` 加一行，否则**静默不跑**。
- 所有 `try` + CleanUp 的分配，上 arena，不要手动追踪。
- `std.compress.flate` 的 container 必须 `.zlib`，`init` 要预分配窗口 buf
  （`std.io.Reader` + buffer），返回的是一个 `Reader` 适配器，要 `.read` 全。
- `std.json.parseFromSlice` 返回 `Parsed(T)`，**记得 `parsed.deinit()`**，
  内部是 arena；而且Arena 释放后 `value` 里切片全部失效 —— 要么在同一个
  处理流程里把所需数据拷出来再释放，要么整体priority用同一个 arena。

**glTF 侧**
- `componentType` 三种都要支持；`normalized` 别忘了报错分支。
- 一个 mesh 多 primitive = 多 RenderObject，别按 mesh 建。
- POSITION accessor 的 min/max 是规范 REQUIREMENT，全信。
- Y-up 转换**只做一次**、集中在一处（放 Gltf.zig 的最后一层转换）；三角形
  绕序问题先用换 cull 模式诊断，别上来就改顶点索引。
- 纹理 image 引用可能是外链文件，也可能是 bufferView（`.gltf` 内嵌二进制）
  —— v1 报"仅支持外链图片文件"，但结构上 images 定义要能分开处理这三种。

**PNG 侧**
- filter marker 是**每行一个字节**，且第一行滤波 marker 是 `type=0` 结尾
  的额外 `filter==4`（Paeth）依赖完整的一圈字节，别按字节位切。
- 多个连续 IDAT 的 zlib 流按拼接、一次性解压。
- tRNS 对 truecolor 也有单像素透明格式（v1 可仅支持类型 3/4/6 的 alpha
  变体，Type 2 的 tRNS 直接报错），别试图全兼容。

**渲染侧**
- Vulkan image layout 三段转换缺一不可；`COPY_BUFFER_TO_IMAGE` 必须在
  Transfer queue 且 `renderpass` 外（如果 Current design 的 Sync/framebuffer
  不允许，就另外建个一次性 command buffer；这在我们当前架构里是独立
  辅助 cmd buffer，别渲染主事件录）。
- D3D11 那边 `CreateTexture2D` 的初始数据传 pixels 时，**stride 一定 =
  width*4 对齐**（不对齐会黑，而且不容易定位到原因）。
- shader 端 t0/s0（HLSL）与 binding（GLSL）两个源文件要一起改，编译
  链路 fxc 和 glslc 都要过一遍；改了 shader **记得删 ++到重编产物**
  （着色器编译是批处理脚本，不在 zig build 里）。
