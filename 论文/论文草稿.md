## 摘要

三维渲染引擎是图形学研究成果落地为应用软件的核心载体，但主流商业引擎（Unity、Unreal Engine）体量庞大、封闭性强，不适合作为教学与小型工具的开发底座。本文设计并实现了一个轻量级跨平台渲染引擎 ShadeFlow，重点解决两个问题：**如何在同一套引擎 API 下适配多个图形 API**，以及**如何将原生渲染引擎嵌入现代应用框架**。

在后端层面，本文提出了以"显式管线模型"为核心的渲染后端抽象：管线状态（光栅化、深度、混合、图元拓扑）在管线创建时一次性定型（D3D12 烘焙为 PSO，Vulkan 烘焙为 VkPipeline），绘制时只传递常量与纹理，不存在即时状态的残留，从机制上消除了状态机式抽象（如 OpenGL/D3D11）中"改一个状态影响后续所有绘制"的隐患。该抽象已在 Direct3D 12、Vulkan 两个后端上实现，并经由 MoltenVK 兼容层支持 macOS。

在宿主层面，引擎核心以纯跨平台模块实现，通过稳定定义的 C-ABI 导出给 WinUI 3 宿主，以 Composition 模式（SwapChainPanel + 交换链互操作）实现原生渲染与托管 UI 的合成。在此之上构建了一个小型三维场景编辑器，支持几何体添加（参数对话框录入）、视口点击拾取、场景树/属性面板/三维视口三视图联动、地面网格吸附、场景的 JSON 序列化存取。资产管线支持 glTF 2.0（含 GLB）导入、按材质拆分渲染对象、右 handed 到左 handed 坐标系转换与纹理的 GPU 上传采样。

测试结果表明，同一套引擎代码在 Windows（D3D12）、Linux（Vulkan）、macOS（MoltenVK）三个平台上均可正确渲染同一场景，编辑器功能在两后端下行为一致。

**关键词**：渲染引擎；Direct3D 12；Vulkan；跨平台；WinUI 3；C-ABI；glTF

## 第一章 绪论

### 1.1 研究背景与意义

图形 API 正处于从"全局状态机"向"显式资源与管线"范式迁移的完成期。D3D11/OpenGL 时代的即时模式（immediate mode）将大量渲染状态（绑定的着色器、顶点格式、混合方式等）挂在设备上下文上，驱动需要在每次绘制时推断状态差异，开销大且行为难以推理。D3D12 与 Vulkan 将这些状态显式化：管线状态对象（PSO / VkPipeline）在创建时定型，资源绑定通过描述符堆/描述符集显式声明，同步由应用负责。这一范式带来了性能与可预测性，但也显著提高了引擎开发的心智负担——同样的概念在两个 API 中名称、粒度、约束各不相同。

对教学和小型工具而言，商业引擎过重，而直接面向 D3D12/Vulkan 编程又缺乏结构。一个**结构清晰、规模可控、能同时跑在多平台多后端**的渲染引擎，恰好填补这一空档：它既是理解现代图形 API 的教学载体，也可以作为轻量三维工具（查看器、编辑器）的开发底座。

本课题的意义在于：

1. **抽象层设计**：给出并实现一套"显式管线模型"的后端中立契约，用一份引擎代码同时驱动 D3D12 与 Vulkan，并论证两者的概念映射关系；
2. **宿主互操作**：探索原生引擎与 WinUI 3（托管、Composition 渲染）共存的工程路径——C-ABI 边界、交换链互操作、输入翻译分层；
3. **完整性**：从资产导入（glTF/纹理）到交互编辑（拾取/属性面板/场景存取）形成闭环，而非仅是渲染 demo。

### 1.2 国内外研究现状

- **商业引擎**：Unity/Unreal 通过各自的图形抽象层（GfxDevice / RHI）支撑多后端，但其抽象面向引擎全功能（物理、音频、脚本），代码规模百万行级，不适合直接研读。
- **开源教学引擎**：Hazel/The Cherno、LearnOpenGL 配套代码等聚焦单平台（多为 OpenGL），缺少多后端抽象与现代 API（D3D12/Vulkan）的工程实践；bgfx、wgpu 等跨后端库成熟但以库的形式存在，宿主集成、资产管线、编辑器需自行搭建。
- **GUI 混合渲染**：将原生 D3D 交换链嵌入 UWP/WinUI 应用是微软官方支持的能力（SwapChainPanel/ISwapChainPanelNative），但完整的"编辑器级"集成（输入翻译、DPI、生命周期管理）公开资料零散。

本课题在上述空白处定位：以现代双后端为核心的教学级引擎 + 可用的编辑器宿主。

### 1.3 主要研究内容

1. 渲染后端中立契约的设计（显式管线模型），及其在 D3D12 与 Vulkan 上的实现与概念映射；
2. 宿主/引擎分层：引擎模块不依赖窗口系统与输入设备，独立窗口宿主与 WinUI 3 宿主翻译同一批命令入口；
3. 资产管线：glTF 2.0 / GLB 解析、坐标系转换、纹理上传与采样（两后端各自的资源上传与描述符方案）；
4. C-ABI 互操作层与 WinUI 3 场景编辑器：对象索引簿记、三视图联动、JSON 场景存取；
5. 系统测试：三平台功能验证与两后端性能对比。

### 1.4 论文组织结构

第一章绪论；第二章介绍相关技术与开发环境；第三章论述总体架构设计；第四章按模块论述详细设计与实现；第五章给出测试与分析；第六章总结全文并展望后续工作。

## 第二章 相关技术与开发环境

### 2.1 Zig 语言

引擎以 Zig 0.17 实现。选择 Zig 的理由：(1) 无隐藏控制流（无异常、无隐式构造/析构），资源生命周期显式，适合教学演示"每一步发生了什么"；(2) 编译期元编程（comptime）可在编译期完成后端契约检查——本项目用一段 comptime 代码逐一校验后端模块实现了契约清单中的全部方法，缺一个即编译失败；(3) 交叉编译开箱即用，一套构建脚本产出 Windows/Linux/macOS 目标。

### 2.2 Direct3D 12 与 Vulkan

两者同属显式范式，核心概念映射关系如下（论文正文建议做成对照表）：

| 概念 | D3D12 | Vulkan |
|---|---|---|
| 逻辑设备 | ID3D12Device | VkDevice |
| 命令提交 | ID3D12CommandQueue + Allocator/List | VkQueue + CommandPool/CommandBuffer |
| 管线状态 | ID3D12PipelineState | VkPipeline |
| 资源绑定 | 根签名 + 描述符堆 | 管线布局 + 描述符集/池 |
| 帧同步 | Fence | Fence + Semaphore |
| 交换链 | IDXGISwapChain（FLIP 模型） | VkSwapchainKHR + RenderPass |

### 2.3 MoltenVK

macOS 无原生 Vulkan 驱动，MoltenVK 以 Vulkan-on-Metal 兼容层实现。本项目在 macOS 上通过运行时加载 `libMoltenVK.dylib`，处理了移植性扩展（`VK_KHR_portability_enumeration`、`VK_EXT_metal_surface`、`CAMetalLayer` 注入）。

### 2.4 WinUI 3 与 Composition 模式

WinUI 3 是微软新一代 Windows 应用 UI 框架。其 `SwapChainPanel` 允许应用将自己的交换链呈现内容合成进 UI 树：引擎侧通过 `IDXGISwapChain1` 的互操作句柄交给 `ISwapChainPanelNative::SetSwapChain`，UI 框架负责合成与 DPI 缩放，引擎只管往交换链画帧。

### 2.5 glTF 2.0

glTF 是 Khronos 制定的三维资产传输格式（JSON 描述 + 二进制缓冲 + 图片），GLB 为其单文件容器。本项目实现 CPU 侧解析（含 data URI、外部文件、GLB BIN chunk 三种缓冲来源），每个 primitive 生成一个渲染对象。

## 第三章 总体设计

### 3.1 分层架构

系统自上而下分为四层，依赖方向严格向下：

```
┌────────────────────────────────────────────────┐
│ 宿主层  main.zig（独立窗口） / capi.zig + C#（WinUI 3）│  ← 窗口、输入事件、UI
├────────────────────────────────────────────────┤
│ 引擎层  Engine / scene / view / asset / math / Time │  ← 命令入口、场景管理、资产解析
├────────────────────────────────────────────────┤
│ 渲染门面  Renderer（类型别名 + 契约检查）              │
├────────────────────────────────────────────────┤
│ 渲染后端  backend/d3d12 · backend/vulkan（二选一）    │  ← 各自封装原生 API
└────────────────────────────────────────────────┘
```

三条硬边界：

1. **引擎不认识窗口与输入设备**。引擎只暴露 `cameraZoom / cameraPan / cameraOrbit / cameraSelfRotate / pickAt` 等命令入口；独立窗口宿主在 Zig 侧把 windowkit 事件翻译成命令，WinUI 3 宿主在 C# 侧把 Pointer 事件翻译成同一批命令。翻译发生在不同宿主，消费的是同一份引擎。
2. **引擎不认识后端**。引擎、场景、资产代码只允许 import 渲染门面 `Renderer.zig`（后端类型别名），未选中的后端模块根本不进入编译图——后端切换由构建选项决定，运行时零开销。
3. **宿主不认识后端**。C# 侧只见到 `ShadeFlow_*` C 函数，交换链通过后端中立的 `swapChainInteropHandle()` 获取（非 Direct 后端返回空，互操作不可用即明确失败）。

利用 Zig 的模块机制（相对路径 import 并入当前模块、跨模块只能用构建脚本声明的命名模块），上述边界不是约定而是编译器强制：违反分层的 import 会直接编译失败。

### 3.2 显式管线模型契约

后端契约共 13 个方法 + 1 个导出类型：`initForComposition / initForHwnd / deinit / beginFrame / endFrame / resize / swapChainInteropHandle / createVertexBuffer / createIndexBuffer / createShaderFromFiles / createPipeline / createTexture / draw / drawIndexed` 与 `Pipeline` 类型。

设计原则：

- **状态定型于创建时**：`createPipeline(shader, PipelineState)` 一次性烘焙光栅化/深度/混合/拓扑。引擎中不存在 `setRasterState()` 这类即时接口，后端实现者不可能引入隐藏状态。
- **数据随绘制传参**：`draw(pipeline, vertexBuffer, count, constants, texture)`——常量按帧写入后端自管理的环形缓冲，纹理为可空参数（空则绑定 1×1 白色默认纹理，使无纹理对象复用同一条采样路径）。
- **契约编译期校验**：门面模块用 comptime 遍历契约清单逐一 `@hasDecl` 检查，新后端实现不完整即编译报错。

### 3.3 渲染对象与所有权模型

场景对象统一为"顶点缓冲 + 可选索引缓冲 + 着色器 + 管线 + 可选纹理 + 变换 + 局部包围盒"。所有权的两个关键决定：

1. **着色器堆分配、管线借用**：管线内部持有指向着色器的指针，若着色器按值内嵌于对象，列表扩容挪动后指针悬垂。因此着色器以指针持有（页分配器分配），析构顺序严格为 管线 → 纹理 → 缓冲 → 着色器。
2. **分配器配对**：着色器的分配与释放必须用同一分配器。开发中曾因"GPA 分配、页分配器释放"按页 munmap 了相邻存活对象，退出时在毫不相关的析构点崩溃——此教训写入了代码注释。

### 3.4 拾取与索引空间

拾取基于射线-包围盒（AABB）相交：屏幕坐标反投影生成射线，与每个对象的局部包围盒求交（对象每帧自转，包围盒按局部空间存储，射线反变换到局部空间测试，避免每帧重建）。命中索引在"枚举顺序"（非索引对象在前、索引对象在后）中返回，删除接口使用同一坐标系，删除后索引前移、宿主同步维护——这是编辑器三视图联动的数据基础。

地面参考网格为常驻参照物：独立存储，不进入上述索引空间（不可拾取、不可删除、场景清空不受影响），每帧最先绘制。

## 第四章 详细设计与实现

### 4.1 渲染后端实现

#### 4.1.1 D3D12 后端

- **设备与帧结构**：命令队列 + 命令分配器/列表 + Fence；RTV/DSV 描述符堆之外，另建着色器可见的 SRV 堆（128 槽）与采样器堆（16 槽）供纹理绑定。
- **常量上传**：绘制时按 256 字节对齐写入环形上传缓冲（双后备缓冲各一份），每帧 `beginFrame` 等待 GPU 完成（单帧 in-flight）——与 Vulkan 后端的双帧 in-flight 存在同步深度差异，作为已知待优化项在 5.3 节讨论。
- **纹理上传**：默认堆资源 + 上传堆中转 + `CopyTextureRegion`，屏障序列 UNDEFINED → COPY_DEST → PIXEL_SHADER_RESOURCE；缓冲类资源 MipLevels 必须显式置 1（置 0 返回 E_INVALIDARG，调试代价高，已记录）。
- **带纹理变体**：顶点布局含 TEXCOORD 语义时，着色器自动切换到带纹理的根签名（根 CBV + t0 SRV 表 + s0 采样器表）。

#### 4.1.2 Vulkan 后端

- **描述符拆组**：set0 为按帧的动态 uniform（常量环），set1 为 combined image sampler，每个纹理创建时一次性写好自己的描述符集，绘制时仅切换绑定。
- **纹理上传**：一次性命令缓冲 + staging 中转上传至 device-local，屏障序列与 D3D12 对应。
- **双帧 in-flight**：per-frame 的 fence/semaphore/command buffer，获取链图像信号量与渲染完成信号量分离。
- **坐标差异**：投影矩阵 Y 翻转、SPIR-V 着色器（glslc 编译，已挂入构建流程）。

#### 4.1.3 着色器管理

同一份 GLSL/HLSL 源保持语义一一对应（顶点布局 location/语义一致、常量块字段顺序一致——std140 与 cbuffer 布局差异由字段对齐消解）。内置 Basic3D（顶点色 + 法线光照）与 Basic3DTextured（纹理 + 法线光照）两组，像素着色器均实现 half-lambert 光照与选中金色脉动高亮（利用常量中的预留选择通道）。

### 4.2 数学库与相机系统

自实现 4×4 矩阵、四元数、AABB。相机为轨道模型（目标点 + 距离 + 自身旋转），视图矩阵由相机右/上/前向量直接构造。详细推导见论文附录/项目笔记：《3D渲染透视投影推导》《3D变换矩阵详解》《万向锁问题排查与修复》——其中万向锁一节记录了欧拉角顺序导致的翻转异常及四元数化修复过程，可作为正文案例。

### 4.3 资产管线

#### 4.3.1 glTF 解析

两层 API：纯内存解析（JSON + 缓冲/图片字节表）与文件加载（.gltf 三种缓冲来源 / .glb 单容器）。要点：

- **按 primitive 拆分**：每个 primitive 是独立的渲染对象（独立顶点/索引/材质），有 baseColorTexture 的走纹理路径，否则走 COLOR_0 → 材质 baseColorFactor → 白色的颜色回退链；
- **局部索引**：glTF 索引是 primitive 局部的，合并 part 时由解析器统一加 base_vertex 偏移——测试用例明确防止"预偏移数据 + 二次偏移"的双重偏移错误；
- **右手到左手转换**：位置与法线均在解析时做 X 取反（引擎为左手系），经验证此方案与剔除策略（默认不剔除，因绕序未审计）配合正确；
- **内存所有权**：GLB 的 BIN chunk 指针指向文件字节，所有缓冲/图片表必须拷贝持有，避免悬垂。

#### 4.3.2 纹理链路

图片字节 → zigimg 解码统一为 RGBA8 → `createTexture(pixels, w, h)` 上传 GPU（两后端各自方案见 4.1）→ 绘制时按对象绑定。顶点布局决定着色器变体的机制使 glTF 混合场景（同一模型中有贴图与无贴图 part）自动走各自路径。

### 4.4 C-ABI 互操作层与编辑器

#### 4.4.1 ABI 设计

导出函数覆盖：引擎生命周期（创建/渲染/清理/状态查询）、场景构建（参数化几何体、贴图立方体、glTF 加载、单对象删除）、相机命令、拾取。两个工程决策：

1. **默认着色器**：所有"添加对象"导出的着色器路径参数可空，为空时回退到互操作层在引擎创建时按宿主 exe 目录解析的默认着色器（按后端选择 .cso/.spv）——C# 侧完全无需关心着色器资源；
2. **扁平数据**：几何参数为 C 兼容的 tag + payload 联合体，C# 侧以 `[StructLayout(LayoutKind.Explicit)]` 手工对齐，字段布局变更两侧强制同步（以文档约束）。

#### 4.4.2 编辑器功能与联动

WinUI 3 编辑器包含场景树、三维视口（SwapChainPanel）、属性面板三视图，联动的数据链：

```
视口左键点击 → PickAt(x,y) → 命中索引 → 场景树选中对应节点 → 属性面板显示参数
场景树选中  ─────────────────────────────────────↗
属性面板"应用" → 引擎单删+重建对象 → 索引簿记前移 → 三视图一致
```

- **对象索引簿记**：场景树每个几何体节点持有引擎索引与完整参数（SceneObjectData）；添加、删除、改参（单删+追加重建）、加载场景（清空重编号）均维护"树节点索引 = 引擎枚举索引"不变量；
- **场景序列化**：JSON 格式（version + 对象数组：类型/参数/位置），交互添加与加载重建共用同一条添加路径，保证所见即所存；
- **网格吸附**：添加对话框 X/Z 自动吸附至 0.5 网格、默认 Y 为落地值；地面网格由引擎常驻提供（Y=0 线段拓扑，X/Z 轴着色）；
- **输入翻译**：中键拖动=公转、Shift+中键=平移、Alt+中键=自转、滚轮=缩放（目标距离钳制 + 平滑收敛）、左键=拾取。
